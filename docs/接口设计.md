# LifeAI 接口设计（API 契约）

> 配套：[数据库设计](数据库设计.md)、[AI 设计](AI设计.md)、[页面设计](页面设计.md)
> 后端：FastAPI，自动生成 `/docs`（Swagger）与 `/redoc`。

---

## 1. 通用约定

### 1.1 基础

| 项 | 约定 |
|---|---|
| 前缀 | `/api/v1` |
| 认证 | `Authorization: Bearer <access_token>` |
| 请求/响应 | `application/json`（上传为 `multipart/form-data`） |
| 时间格式 | 入参出参统一 ISO8601 带偏移：`2026-05-01T03:00:00+08:00`（库内存 UTC） |
| 日期格式 | `YYYY-MM-DD`；月份 `YYYY-MM` |
| 字段命名 | 出参 `snake_case`（与数据库一致，前端在 `api/` 层转驼峰亦可，本项目**不转**，减少心智负担） |
| 幂等 | 写操作可选 `Idempotency-Key` 头；AI 确认接口靠行锁（`SELECT ... FOR UPDATE`）保证，**不需要**该头 |
| 追踪 | 响应头返回 `X-Request-Id`，与 `operation_logs.request_id` 对应 |

### 1.2 响应格式

**成功**：直接返回业务数据（2xx），列表统一分页结构。

```json
{
  "items": [ { "id": 1, "title": "买菜" } ],
  "total": 42,
  "page": 1,
  "size": 20,
  "pages": 3
}
```

**失败**：统一错误体，HTTP 状态码语义化。

```json
{
  "code": "TASK_NOT_FOUND",
  "message": "待办不存在",
  "request_id": "0f8c...",
  "detail": { "field": "title" }
}
```

> 禁止在 `message` 中返回堆栈、SQL、密钥（NFR 11.3）。

### 1.3 分页与排序

| 参数 | 默认 | 约束 |
|---|---|---|
| `page` | 1 | ≥1 |
| `size` | 20 | 1～100 |
| `sort` | 见各接口 | 形如 `-created_at`（`-` 表降序） |
| `keyword` | 无 | 模糊匹配标题/备注 |

### 1.4 错误码

| code | HTTP | 场景 |
|---|---|---|
| `VALIDATION_ERROR` | 422 | 参数校验失败（Pydantic） |
| `UNAUTHORIZED` | 401 | 未携带 Token / Token 无效 / 过期 |
| `FORBIDDEN` | 403 | 角色权限不足（如普通用户访问 `/admin/*`） |
| `USER_DISABLED` | 403 | 账号被禁用 |
| `NOT_FOUND` | 404 | 资源不存在**或不属于当前用户**（防信息泄露） |
| `CONFLICT` | 409 | 用户名/邮箱重复、重复确认动作 |
| `QUOTA_EXCEEDED` | 429 | AI 每日额度用尽 |
| `FILE_TOO_LARGE` | 413 | 上传超限（20MB） |
| `UNSUPPORTED_FILE_TYPE` | 415 | 非 pdf/docx/txt |
| `AI_UNAVAILABLE` | 503 | 模型服务超时或不可用 |
| `ACTION_EXPIRED` | 410 | 待确认动作已过期 |
| `INTERNAL_ERROR` | 500 | 未捕获异常（不暴露细节） |

### 1.5 权限矩阵

| 资源 | user | vip | admin |
|---|---|---|---|
| `/tasks` `/expenses` `/life/*` `/diaries` `/budgets` `/shopping-*` | 本人数据 | 本人数据 | 本人数据 |
| `/ai/*` | 基础模型 + 标准额度 | 高级模型 + 高额度 | 同 vip |
| `/documents` 私人文档 | 本人 | 本人 | **不可访问他人** |
| `/analytics/*` | ✅ | ✅ | ✅ |
| `/admin/*` | ❌ 403 | ❌ 403 | ✅ |
| 公共知识（`documents.visibility=public`） | 只读检索 | 只读检索 | 增删改 |

## 4. 待办 `/tasks`（V1.0）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/tasks` | 列表与筛选 |
| POST | `/tasks` | 新增 |
| GET | `/tasks/{id}` | 详情 |
| PATCH | `/tasks/{id}` | 局部更新 |
| DELETE | `/tasks/{id}` | 软删除 |
| PATCH | `/tasks/{id}/status` | 状态切换 |

**GET /tasks** 查询参数：`status`（可多值）、`category_id`、`priority`、`due_from`、`due_to`、`keyword`、`overdue`（true 只看逾期）、`page`、`size`、`sort`、`order`

排序参数（V1.0 实装）：

| `sort` | 含义 | 第二排序键 |
|---|---|---|
| `due_at`（默认） | 截止时间 | 截止时间 → 无截止时间的永远置后 → `id` 倒序 |
| `created_at` | 创建时间 | `id` 倒序 |
| `priority` | 优先级（`high` > `medium` > `low`，不是字母序） | 截止时间升序（空值置后）→ `id` 倒序 |

`order` 取 `asc` 或 `desc`，默认 `asc`。两条约定：

1. **空 `due_at` 永远排在最后**，与 `order` 无关（按「是否为空」当第一排序键，不用 `NULLS LAST` 语法，MySQL 不支持）。
2. 所有排序都补 `id` 兜底，否则相同排序键的记录在翻页时可能重复出现或漏掉。

响应项：

```json
{
  "id": 12, "title": "去超市买牛奶和鸡蛋", "description": null,
  "category_id": 31, "category_name": "购物",
  "priority": "medium", "status": "todo",
  "due_at": "2026-05-02T07:00:00+08:00",
  "remind_at": "2026-05-02T06:30:00+08:00",
  "completed_at": null, "is_overdue": false,
  "source": "ai", "created_at": "2026-05-01T10:00:00+08:00"
}
```

**POST /tasks** 请求体（校验规则）：

| 字段 | 类型 | 必填 | 校验 |
|---|---|---|---|
| title | string | ✅ | 1～120 字符，去首尾空白后非空 |
| description | string | ❌ | ≤2000 |
| category_id | int | ❌ | 必须存在且 `scope='task'` 且属于本人或系统 |
| priority | enum | ❌ | low/medium/high，默认 medium |
| due_at | datetime | ❌ | ISO8601 |
| remind_at | datetime | ❌ | 必须早于 `due_at`（若两者都有） |

**PATCH /tasks/{id}/status**：`{ "status": "done" }` — 置 `done` 时自动写 `completed_at`；置回非 `done` 时清空。

## 7. 首页 `/dashboard`（V1.0）

**GET /dashboard/overview** 响应：

```json
{
  "tasks": { "todo": 5, "doing": 2, "done": 12, "cancelled": 1, "overdue": 2, "today_due": 3 },
  "expense": { "current_month_total": "1280.50", "last_month_total": "990.00", "today_total": "88.00" },
  "recent_7d": [ { "date": "2026-10-27", "expense": "0.00" }, { "date": "2026-10-28", "expense": "12.50" } ],
  "focus_tasks": [
    { "id": 12, "title": "买菜", "due_at": "2026-11-02T20:00:00+08:00", "status": "todo", "is_overdue": false }
  ]
}
```

> `focus_tasks` 是「逾期 + 今日到期」的列表（`status IN ('todo','doing')`），
> 按 逾期最多 3 条 + 今日到期最多 2 条取，合计最多 5 条，逾期在前；
> 每段内部按 `due_at` 升序、`id` 降序。`is_overdue` 由服务器时间判断，前端不自己算。
> **逾期与今日到期互不重叠**：
>
> | 字段 | 条件（均要求 `status IN ('todo','doing')` 且未删除） |
> |---|---|
> | `tasks.overdue` | `due_at < 现在`（全量计数） |
> | `tasks.today_due` | `现在 <= due_at < 明天北京时间 00:00`（全量计数） |
> | `focus_tasks` | 逾期取最多 3 条 + 今日到期取最多 2 条，拼接 |
>
> 两个数字统计的是**全量**，而列表是**配额制**，所以列表条数可能少于 `overdue + today_due`
> —— 这是有意的：如果按「两类合并后取最早的 5 条」，逾期一多，今天到期的那条就会被历史欠账挤掉，
> 而当天该做的事恰恰是它。今天上午已经过点的待办只计入 `overdue`，不再重复计入 `today_due`。
> 「今日」「本月」按北京时间半开区间；`recent_7d` 恒 7 个点（含今天），无数据的日期补 `"0.00"`。
> 统计口径见「数据库设计」3.3 / 3.5，全部由真实数据聚合，不缓存假数据。

## 12. AI 助手 `/ai`（V1.1）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/ai/chat` | 发送消息，非流式（A4 已实现，无工具；A5 起返回 pending_action） |
| GET | `/ai/sessions` | 会话列表（A3） |
| POST | `/ai/sessions` | 新建会话（A3，请求体可省略） |
| GET | `/ai/sessions/{id}` | 会话详情（A13，字段与列表每一项完全一致） |
| GET | `/ai/sessions/{id}/messages` | 消息历史（分页，A3） |
| PATCH | `/ai/sessions/{id}` | 改标题（A3） |
| DELETE | `/ai/sessions/{id}` | 删除会话（A3，软删） |
| POST | `/ai/actions/{id}/confirm` | **确认写入**（行锁保证幂等，无需请求头） |
| POST | `/ai/actions/{id}/cancel` | 取消待确认动作 |
| GET | `/ai/quota` | 今日额度使用情况 |

**POST /ai/chat**

```json
{ "session_id": 3, "message": "明天下午三点去超市买牛奶和鸡蛋" }
```

`session_id` 省略则新建会话。

响应 `200`：

```json
{
  "session_id": 3,
  "message_id": 88,
  "reply": "已为你整理好购物待办，请确认后保存。",
  "intent": "create_task",
  "pending_action": {
    "id": 21,
    "action_type": "create_task",
    "expires_at": "2026-05-01T10:30:00+08:00",
    "preview": {
      "title": "去超市购物",
      "category_id": 31,
      "category_name": "购物",
      "priority": "medium",
      "due_at": "2026-05-02T15:00:00+08:00",
      "items": ["牛奶", "鸡蛋"]
    }
  },
  "usage": { "token_in": 320, "token_out": 96, "quota_remaining": 47 }
}
```

> `pending_action` 存在时表示「需用户确认」，前端必须渲染确认卡片，**此时不写入任何业务数据**。

> **当前实现（A5 第 4 步）**：`pending_action` 已接通，`preview` 的实际字段是
> `title` / `due_at` / `priority` / `category_name`（模型给的原文）+ `category_id` / `due_at_text` / `priority_text`（服务端补的可读值）。
> 一次只出**一张卡**（`MAX_DRAFTS_PER_REPLY = 1`），没有 `items` 数组。
> 仍未实现：`intent`、`usage.quota_remaining`（A6 额度）。
> 模型把工具参数交坏两遍时返回 **502 `MALFORMED_TOOL_ARGS`**：这一轮不产生卡片，库里留一条 `status=failed` 的 assistant 行（含模型的原文与失败原因），前端应提示「稍后重试」。
> 其他失败（超时/限流/未配置）仍返回对应 5xx 统一错误体，库里保留 `status=failed` 行，消息列表可见，但不参与下一轮上下文。

> **当前实现（A5 第 6 步）**：`pending_action` 多了 `status` 字段（`pending` / `confirmed` / `cancelled` / `expired`），
> 并且 `GET /ai/sessions/{id}/messages` 的每条消息也会带 `pending_action`（没有卡片则为 `null`）。
> 这样刷新页面后卡片能原样恢复，已处理的卡片显示成「已创建 / 已取消」而不是消失。
> **`pending_action.created_id`** 取自 `ai_pending_actions.result`（确认时写进去的 `{"type","id"}`），
> 所以「查看待办 ▸」链接刷新后也在；`result` 被改坏时降级成 `null`，不让列表 500。
> **消息列表是读路径，不改状态**：已过期的卡照实返回 `status=pending`，用户真去点时由确认接口置 `expired` 并回 410。

> **当前实现（A6 只读工具）**：模型多了一个 `query_tasks` 工具，可以**先查再答**。
> - 一次提问内最多 `MAX_ROUNDS = 3` 轮：模型申请查询 → 服务端执行 → 结果以「【系统：已执行 query_tasks，…】」的文本形式回灌 → 模型再说人话。
> - 查询结果**不进库**：它是这一轮的临时上下文，不是对话历史。刷新页面看到的仍是用户的提问和模型的话。
> - 只读链路**不写任何业务表**、不产生卡片、不改会话状态。
> - 默认只查未完成（`todo` + `doing`）；要查已完成的，模型必须显式传 `status="done"`。
> - 单次最多返回 10 条（`limit` 在参数校验和 `tasks_crud.search` 里各夹一次）。
> - 多轮调用的 token 与耗时**累加**后写进 `ai_usage_logs`，不是只记最后一轮。
> - 同一轮里既申请查询又申请新建：以新建为准，查询被丢弃（不留半截记录）。

> **当前实现（A7 改待办）**：写入类工具多了 `update_task`，模型能改**已有**的待办，
> 但走的仍是「草稿 → 确认卡 → 用户点确认」同一条路，不能直接写库。
> - 参数：`task_id`（必填）以及 `title` / `due_at` / `priority` / `category_name`（改哪些给哪些）。
>   `task_id` 必须来自上一轮 `query_tasks` 的结果，服务端**不信**模型给的 id：
>   `create_draft` 与 `execute` 各用 `user_id` 查一次，查不到（含别人的、软删的）返回 404。
> - `preview` 比新增多一个 `before` 段（`task_id` / `title` / `due_at` / `priority` / `category_id`），
>   让用户点确认前能看出「改的是哪一条、原来长什么样」。
> - **不给 `None` 赋「清空」语义**：没提到的字段一律保持原值。清空截止时间、勾完成这类操作
>   留给看板，不在对话里做。
> - `action_type` 的 ENUM 新增 `update_task`（迁移 `1285ee39d2bb`），与新建共用同一套
>   状态机（pending → confirmed / cancelled / expired）与行锁幂等。
> - 待办与卡片状态在**同一个事务**里提交（`tasks_crud.update(..., commit=False)`），
>   写表失败时卡片保持 `pending`，可以重试。

> **当前实现（A8 记一笔支出）**：写入类工具多了 `create_expense`，模型能从一句话里
> 抽出一笔账并出卡（例如「昨天中午吃饭花了 38 块，支付宝」）。
> - 参数：`amount`（必填，> 0，两位小数）、`type`（`expense` / `income`，默认支出）、
>   `category_name`、`account`、`occurred_at`、`note`。模型只认**名字**，不认 id。
> - 分类按 **expense 域**解析：`_SCOPE_BY_ACTION["create_expense"] = "expense"`。
>   「购物」在 task 域是 id 18、在 expense 域是 id 3，查错域不会报错，只会静默记错账。
> - **分类名查不到就落 0（未分类）并照常出卡**，不返回 422：钱数和时间比分类更值钱，
>   分类可以让用户在卡片上改。前端把 `category_id = 0` 显示成「未分类」。
> - `occurred_at` 没给时由服务端补成出卡时刻（`to_beijing_iso(now_utc())`，别用
>   `now_beijing()`，会多 8 小时）。
> - `preview` 多三个可读字段：`amount_text`（`¥38.50`）、`type_text`（支出 / 收入）、
>   `occurred_at_text`（北京时间 + 星期）。
> - 确认时写 `expenses` 表并置 `source = "ai"`（`EXPENSE_SOURCES = ("manual", "ai")`），
>   与卡片状态同事务（`expenses_crud.create(..., source="ai", commit=False)`）。
> - `ExpenseCreate.category_id` 是 `ge=1`，未分类的 0 过不了模型校验，所以 `_write_expense`
>   先用 `category_id or 1` 构造、再把真实值（可能是 0）覆盖上去。

> **当前实现（缺信息时的反问口径）**：服务端**不做**补问逻辑，这是模型行为，靠
> `prompts.TOOL_RULES` 第 4、5 条与工具 description 约束：
> - 信息不全时**一次把缺的全问完**，逐条列出，此时不出卡。
>   账需要金额 / 用途 / 支付方式；待办需要做什么 / 什么时候 / 哪一类。
> - **问过一轮就够了**：用户补了一部分就按默认值出卡，不再追问细节。
>   用途落「其他」、支付方式记「现金」、时间记现在 —— 都能在确认卡上改。
> - 因此 `create_expense` 只有 `amount` 是必填，`account` 的字段说明里**不能**写
>   「没提就问」（写了就会出现「有金额却死活不出卡」）。
> - 这些要求由 `tests/test_ai_clarify.py` 钉住：提示词被删/改弱时会红。

> **当前实现（待办优先级的给法）**：同样是模型行为，规则写在 `create_task` 的
> `priority` **参数说明**里（而不是系统提示词）——它必须和 `due_at` 一起看：
> - 有明确时间且在 3 天内 → `high`；有明确时间但更远 → `medium`；没有任何时间 → `low`。
> - 用户明确说「很急」「重要」「不急」「随便」时，以用户的话为准（「这周五看电影，不急」→ low）。
> - **这一项不用问用户**，否则又回到「一个一个问」。
> - `update_task` 的 `priority` 仍保持「用户没提就不要传」，不受这套规则影响。

> **当前实现（A9 查账）**：`query_expenses` 是第二个只读工具，立刻执行、不落卡、不写库，
> 结果折成一段「【系统：已执行 query_expenses，…】」回灌给模型（做法同 A6）。
> - 参数：`date_from` / `date_to` / `type`（expense|income）/ `category_name` / `account` / `limit`，
>   全部可选 —— 「我一共花了多少」一个条件都不给也得能查。
> - **合计按全部命中记录算，只有明细受 `limit` 约束**（默认 5、上限 10）。
>   回灌里先给「命中记录：共 N 条」「支出合计 / 收入合计」，再列明细，
>   就是为了避免模型把「这 5 条」说成「一共」。实现见 `expenses_crud.search`：
>   明细与合计是两条 SQL，合计那条不带 limit。
> - 时间是**北京时间的整天**：`2026-11-01` 到 `2026-11-03` = 1 号 00:00 ≤ occurred_at < 4 号 00:00。
>   起止说反了自动换过来，不降级成「不限时间」。
> - 分类按 `expense` 域解析（「购物」在这里是 3，task 域那个是 18）；分类名不存在直接返回空，
>   并明确告诉模型「没有这个分类」，不让它当未分类去查。
> - 失败路径与 `query_tasks` 一致：参数校验不过就降级成无筛选查询，并在回灌里说明原因。
>
> **当前实现（A10 删待办）**：`delete_task` 是第四个写入类工具，与 `update_task` 同一套
> 「出卡 → 确认 → 写表」流程，区别在于**它不可逆**，所以三处更严格：
> - 参数只有 `task_id`（必填，必须来自 `query_tasks` 结果）与 `reason`（可选，只进卡片、
>   不进数据库）。没有批量字段 —— 一次回复最多采纳一份草稿，本来也表达不了「全删」。
> - 卡片 `preview` 带一份 `gone` 快照（标题 / 时间 / 优先级 / 分类，含 `due_at_text`
>   与 `priority_text`）。光有 `reason` 不够：模型抄错 id 时，`gone` 里露出的会是另一条
>   待办的名字，那是用户最后一道逃生机会。
> - 确认时 **`payload_override` 一个字段都不接受**（非 null 直接 422
>   `ACTION_PAYLOAD_INVALID`）：删除卡没有「可改内容」，若按字段白名单挑着传，
>   前端塞一个 `task_id` 进来就能换一条删。
> - 落库走 `tasks_crud.soft_delete(..., commit=False)`：只写 `deleted_at`，行仍在，
>   与「卡片置 confirmed」同一事务。卡片躺在屏幕上时那条待办若已被页面删掉，
>   确认回 404「要删除的待办不存在，可能已经删过了」，卡片保持 pending。
> - `action_type` ENUM 增加 `delete_task`（迁移 `6e343c615ded`）。
>
> **当前实现（A11 长对话的前情摘要）**：接口签名不变，变的是**送进模型的历史**。
> - 上下文 = system 提示词 +（可选）一条「【前情摘要】…」user 消息 + 最近 20 条原文。
>   20 条 ≈ 10 轮，窗口外的旧消息会被压缩成一段摘要，不再整体丢弃。
> - 触发条件：消息总数 - 窗口条数 ≥ 12。**短对话一次都不多调模型**，摘要成本不摊到每轮。
> - 增量更新：只读「上次摘要之后、本次窗口之前」那一段（`summary_until_id` 指针），
>   与旧摘要合并写回 `chat_sessions.summary`。全量重摘要的 token 会随轮数线性增长。
> - 摘要 ≤ 200 字，只写用户自己的事（稳定事实 / 约定 / 已办成的事 / 未决事项），
>   **不写助理说过什么、给过什么建议** —— 实测 300 字时模型会把「番茄炒蛋怎么练」
>   这类临时输出也记进去，挤占真正有用的信息。
> - 摘要失败（超时 / 限流 / 空回复）只记 warning：这一轮用最近 20 条原文照常回答，
>   指针不推进，下一轮还会重试。宁可忘事，不能答不出话。
> - 摘要存会话列，不产生消息行，`GET /ai/sessions/{id}/messages` 看不到它。
> - 摘要那次调用的 token 单独记一条 `ai_usage_logs`：`purpose=chat`、`error_code=summary_call`
>   （`purpose` 是 NOT NULL ENUM，加一个取值要改库约束，用标记筛更划算）。
> - 新迁移 `a11session`（`chat_sessions` 加 `summary` / `summary_until_id`）。
>
> **当前实现（A11 补丁：反问与重复出卡）**：真机长对话里暴露了两个行为问题，都在服务端收口。
> - **反问不回灌**：模型上一轮的反问（带问号、≤120 字）在拼上下文时替换成
>   「（已向用户反问过一次，用户没有回答，此事暂不处理）」。不替换的话，它会把这句
>   当成「还没办完的事」，用户换了话题还追一句「水果的事明天再说」（实测第 3 轮）。
>   用户自己说的话不受影响；带工具调用的行本来就被跳过，不会误伤。
> - **已发的卡在历史里可见**：带确认卡的助手消息补一句「（这一轮你已经发过确认卡，
>   用户还没确认）」，已处理的标「已确认 / 已取消 / 已过期」。模型看不见这张卡，
>   就会以为没发出去、再发一次。
> - **同一会话同时只留一张待确认的卡**（按内容区分，不是一律不让出卡）：
>   - 模型要发的是**已经挂着的那件事**（任务卡比标题、记账卡比金额+分类）→ 不建第二张，
>     这一轮正文改成「上面那张卡还在等你确认；确认或取消之后，再说新的事。」
>   - 是**另一件事** → 照常建新卡，同时把旧卡标成 `expired`（不删行，用户问起还能答），
>     屏幕上始终只有一张能点的。感觉判不准时宁可放行，不吞用户的话。
>   - 判据在 `pending.is_same_item`，跳过动作在**解析阶段**做
>     （`parse_tool_calls(..., skip=...)`），因为模型常常一口气交两个调用——
>     先重申旧的那张、再说新的一张（真机会话 118 的原样调用），
>     若等「一次只接一张卡」的截断先生效，用户要的新事就被踢掉了。
> - **「只说不做」补一次**：正文里出现「我整理了一条待办 / 一笔账 / 删除 / 待确认」
>   这类写入承诺、这一轮却没有任何工具调用时，服务端把工具声明和一句系统提示一起
>   再发一次（`tool_flow._nudge_messages`），让模型真的把工具调出来。
>   - 只补一次，不无限追；只认写入说法（「我整理了一下你的三个问题」不算）。
>   - 补问后仍没调工具：正文换成「这次没记下来……」，`error_message` 记
>     `模型说了要整理，但没有真的调用工具（已补问一次）`。宁可让用户知道没记上，
>     也不留一句兑现不了的承诺。
> - **模型把旧卡又发一遍，而用户说的是另一件事**：先按上面的规则拦下，再补问一次
>   （`tool_flow._redoS_hint`）——点名「你发的是已经挂着的那件事」、把用户这一句原话
>   贴回去。真机会话 120 里，旧卡是「买水果」，用户说「帮我记个待办：周五下午三点
>   去银行」，模型第二次还是发「买水果」；当时直接回「上面那张卡还在等你确认」，
>   用户要的那件事整句消失。补问后若还是发旧的，正文换成「这次没记下来……」
>   而不是「上面那张卡在等你确认」，因为后者会让用户以为只是旧卡挡着。
>   判据 `_origin_is_new_task`：用户这句带「记东西」的意图、且去掉旧卡标题后还剩
>   实际内容才算「另一件事」——所以「提醒我买水果」在旧卡是「买水果」时不补问。
> - 代价：极少数轮会多一次模型调用（真机约 1/3 的「漏调」场景会触发），
>   命中后 `ai_usage_logs` 的 token 里自然包含这一次。
> - **总开关**：`Settings.llm_tools_enabled`（默认 true）。关掉后退回 A4 的纯聊天：
>   不发 tools、提示词不讲工具规则、不补问。
>
> **当前实现（A12 改账 / 删账）**：消费记录补齐「改」和「删」，与 A10 删待办同一套路
> （出卡 → 用户点确认才写库 → 行锁防重复）。
> - 两个新工具：`update_expense`（`expense_id` 必填 + 只传要改的字段）、
>   `delete_expense`（`expense_id` + 可选 `reason`）。账目没有标题，`expense_id`
>   只能来自 `query_expenses` 的结果；工具描述里写死了「多笔像的时候反问用户」。
> - 改账卡带 `before` 快照和 `changed`（`["amount"]` 这样的字段名列表），前端照它渲染
>   「旧值 → 新值」。**分类在算 diff 之前就把名字解析成 id**，否则模型说「改成餐饮」
>   时两边 id 都是原分类，卡片会漏掉这一行、点确认后库里分类却真的换了。
> - 什么都没改到的卡不建：模型把原值又抄一遍时直接 422「这次没有需要修改的内容」。
>   真机会话 130 就出过 `changed=[]` 的卡，点确认回「已按这张卡改好」而库里一字未动。
> - 删除是软删（`deleted_at`），卡片上写明「这条账不会出现在列表里」；
>   删除卡不接受 `payload_override`（直接 422），因为「确认」就是删，没有可改的字段。
> - 新迁移 `a12pending`：`ai_pending_actions.action_type` ENUM 加这两项。
> - **同会话历史污染修复**：带工具调用的助手行不再被整条丢掉，而是替换成
>   「（这一轮你调用过工具：update_expense；结果已经交给用户确认）」。
>   跳过的话，模型只记得自己说过「我整理了一条修改」，下一轮会顺着惯性重复上次的动作
>   ——真机会话 130 里用户说「把 7 块那笔删掉」，它又发了一次 `update_expense`。
>
> **当前实现（A13 会话详情）**：`GET /ai/sessions/{id}` 补齐。
> - 返回体与 `GET /ai/sessions` 列表里的每一项**完全一致**（同一个 `SessionOut.from_model`），
>   前端不必写两套渲染。
> - 判定与 `PATCH` / `DELETE` 相同：不存在、已软删、不是自己的，一律 404，不泄露 id 是否存在。
> - `message_count` / `last_message_at` 是会话表上的冗余计数，**不是实时 COUNT**：
>   手写插消息的测试数据不会让它变，只有走 `service.chat` 才会 `touch_session`。
> - 前端用法：打开会话时与消息列表并行拉一次；列表里那份只当兜底
>   （`currentSession = activeSession || 列表项`），刷新后标题立刻有，不依赖列表是否翻得到。

**POST /ai/actions/{id}/confirm**

```json
{ "payload_override": null }
```

`payload_override` 允许用户在前端修改预览内容后提交（`null` 表示按原草稿）。

响应 `200`：

```json
{
  "action_id": 21,
  "action_type": "create_task",
  "status": "confirmed",
  "preview": { "title": "去买菜", "due_at_text": "2026-11-14 15:00（周六）", "category_id": 18, "category_name": "购物", "priority": "medium", "priority_text": "中" },
  "created": { "type": "task", "id": 45 },
  "executed_at": "2026-11-08T15:12:12+08:00"
}
```

错误：`409 ACTION_NOT_PENDING`（已确认/已取消，重复提交）、`410 ACTION_EXPIRED`（超过 30 分钟）、`404 NOT_FOUND`（非本人动作）、`422 ACTION_PAYLOAD_INVALID`（`payload_override` 不合法）。

> **当前实现（A5 第 5 步）**：
> - **幂等靠的是行锁，不是请求头**。文档早期写过「强制 `Idempotency-Key`」，实现时否掉了：
>   确认请求由 `SELECT ... FOR UPDATE` 锁住那一行 pending 记录，状态必须是 `pending` 且未过期才继续，
>   写完业务表后在**同一个事务**里把状态改成 `confirmed` 一起提交 —— 并发两次只有一次能成功，第二次拿到的就是 409。
>   客户端少了「先生成 UUID 再重试」这套负担，服务端也不会因为重复 key 报假错。
> - **原子性**：待办的 `INSERT` 与卡片置 `confirmed` 同属一个事务（`tasks.crud.create(..., commit=False)`），
>   写业务表抛任何异常都会整体回滚，卡片退回 `pending`，不会出现「卡片显示已确认但没有待办」。
> - **`payload_override` 走白名单**：只认 `title` / `due_at` / `priority` / `category_name` / `category_id`，
>   其余键（`user_id`、`status`、`id`、`completed_at` 等）一律丢弃，前端改不了归属和完成状态。
> - `created` 目前只有 `create_task` 一种（`{"type": "task", "id": <新待办 id>}`）；没有 `extra` 字段。

**POST /ai/actions/{id}/cancel** 响应 `200` → 同上结构，`status` 为 `cancelled`、`created` 为 `null`。
错误：`409 ACTION_NOT_PENDING`、`410 ACTION_EXPIRED`、`404 NOT_FOUND`。取消后同一张卡不能再确认。

**GET /ai/quota** 响应：

```json
{ "daily_quota": 50, "used_today": 3, "remaining": 47, "reset_at": "2026-05-02T00:00:00+08:00" }
```

| 允许类型 | `pdf`、`docx`、`txt`（按扩展名 + MIME 双重校验） |
| 大小 | ≤20MB |
| 文件名 | 去路径、去特殊字符，长度 ≤100 |
| 存储 | `uploads/{user_id}/{uuid}.{ext}` |
| 去重 | 同用户 `sha256` 相同则返回 409 |

响应 `202`：

```json
{ "document_id": 5, "status": "pending", "task_id": 9, "message": "已进入解析队列" }
```

**GET /documents/{id}/task** 响应（轮询）：

```json

```

## 17. 实现约定

1. **路由分层**：`api/v1/endpoints/{module}.py`，只做参数绑定与调用，业务逻辑在 `services/`。
2. **依赖注入**：所有受保护路由统一 `Depends(get_current_user)`；`user_id` 不来自请求体。
3. **响应模型**：每个接口声明 `response_model`（Pydantic Schema），禁止裸返 ORM 对象。
4. **错误处理**：业务异常统一抛 `AppError(code, message, status)`，由全局异常处理器转错误体。
5. **审计**：`task.create`、`expense.create`、`document.delete`、`auth.login`、`admin.user.update`、`ai.action.confirm` 六类操作必须写 `operation_logs`。
6. **AI 接口超时**：前端 Axios 对 `/ai/*` 单独设 60s 超时，其余 15s。
