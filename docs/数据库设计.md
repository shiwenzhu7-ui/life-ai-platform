# LifeAI 数据库设计

> 配套文档：[项目规划](项目规划.md)、[接口设计](接口设计.md)、[AI 设计](AI设计.md)
> 适用版本：V1.0 起逐步启用，表结构在 V1.0 一次性设计到位（见「建表版本」列）。

---

## 1. 通用约定

| 项 | 约定 |
|---|---|
| 数据库 | MySQL 8.0+ |
| 引擎 / 字符集 | `InnoDB` / `utf8mb4` / `utf8mb4_0900_ai_ci` |
| 主键 | `id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY`（`categories` 用 `SMALLINT`） |
| 外键 | 逻辑外键（不建 `FOREIGN KEY` 约束），由应用层保证；**唯一索引与普通索引照常建立** |
| 时间字段 | `created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`、`updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` |
| 时间存储 | **统一 UTC**（`DATETIME` 不带时区），应用层唯一的 `core/time.py` 负责转换；API 输出 ISO8601 带 `+08:00` |
| 软删除 | **仅 `chat_sessions` 保留**：`deleted_at DATETIME NULL`，查询默认 `deleted_at IS NULL`。`tasks` / `expenses` / `documents` 自迁移 `e1harddelete` 起改为**硬删除**（2026-11-11 决策，理由见 §2.1）；`categories` / `users` / `shopping_*` 仍保留该列但暂未使用 |
| 金额 | `DECIMAL(12,2)`，禁止 `FLOAT` |
| 枚举 | 使用 MySQL `ENUM` 或 `VARCHAR + 应用层校验`，本文档统一用 `ENUM` 便于自解释 |
| 命名 | 表名复数蛇形；字段蛇形；索引 `idx_` 前缀；唯一索引 `uk_` 前缀 |
| 用户外键 | `user_id BIGINT UNSIGNED NOT NULL`，对应 `users.id` |
| 「0」语义 | 需要「系统级/总预算」等语义的关联字段用 `0` 而非 `NULL`（规避 MySQL 唯一索引多 NULL 不冲突的问题） |

### 1.1 为什么「表一次建全字段」

V1.0 只用到 4 张表，但 `users` 表在 V1.0 就建好 `password_hash`、`auth_source`、`role` 等字段（V1.0 不用）。这样 V1.2 加用户系统时**不需要 `ALTER TABLE`**，也避免历史数据回填迁移。代价是 V1.0 的表比实际需要宽，可接受。
> 实际执行偏差：V1.0 只建了 `users` 的 4 列（`id`/`username`/`nickname`/`created_at`），V1.2 仍补了一次 `ALTER TABLE`（迁移 `b1users`）。配额字段随后在 `c1noquota` 中删除。

## 2. 实体关系概览

```text
users ─┬─< tasks            （待办）
       ├─< expenses  >── categories
       ├─< budgets   >── categories
       ├─< shopping_lists ─< shopping_items
       ├─< diet_records / water_records / exercise_records
       ├─< sleep_records / mood_records / diaries
       ├─< documents ─< document_chunks  ──▶ Milvus（向量）
       ├─< chat_sessions ─< chat_messages ─< ai_pending_actions
       ├─< ai_usage_logs / async_tasks / notifications
       └─< operation_logs（本期不建）

categories：scope 区分用途（消费/待办/购物/饮食/运动/心情/收入）
           owner_user_id = 0 表示系统预置
```

### 2.1 删除语义：硬删除为主，仅会话保留软删（2026-11-11）

| 表 | 删除方式 | 理由 |
|---|---|---|
| `tasks` / `expenses` / `documents` | **硬删除**（`DELETE`） | 用户要的是「删干净」。软删要求全表每一处查询都记得补 `deleted_at IS NULL`，漏一处就是把已删数据算进统计；硬删由数据库保证，不靠人记 |
| `chat_sessions` | 软删除 | 对话历史对排查问题有价值，且会话不会被计入任何金额/数量统计，漏过滤的代价小 |
| `categories` / `users` / `shopping_*` | 列保留、暂无删除入口 | 目前没有删除功能，等真做管理后台再决定 |

三条附带结论：

1. `documents` 硬删后，唯一索引 `uk_documents_user_sha` 不再与「已删除行」冲突，**删掉后可以重传同一份文件**（软删时代这一直是个坑）。
2. 迁移 `e1harddelete` 在删列前会 `DELETE FROM ... WHERE deleted_at IS NOT NULL` —— 否则旧软删行失去标记后会「复活」出现在列表里。审计日志已在 V1.2 取消（见 `需求规格说明书.md` §11.1 例外说明），所以不留历史行不损失信息。
3. `downgrade` 只能把列加回来（全 NULL），被物理删除的行回不来 —— 这是硬删的固有代价，已接受。

### 3.6 `shopping_lists` — 购物清单

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|

| note | VARCHAR(255) | NULL | |
| status | ENUM('active','archived') | NOT NULL DEFAULT 'active' | 归档不改名；改名由应用层负责，见下 |
| created_at / updated_at / deleted_at | DATETIME | | `deleted_at` 保留但未使用（与 categories / users 同），删除是硬删 |

索引：

- `idx_shopping_lists_user(user_id, status)`
- `uk_shopping_lists_user_name(user_id, name)` **UNIQUE**（V1.4 补，迁移 `f1shopname`）—— 统计范围含已归档的清单

> **归档时的名字腾挪**：唯一索引不看 `status`，所以同一用户下不可能存在两张同名清单（哪怕一张已归档）。
> 为了让「归档 → 重建同名清单」可行，归档那一刻应用层把被归档的那张改名为 `名字(1)`、`名字(2)`……
> （先剥掉末尾已有的 `(n)` 再加号，避免叠成 `周末(1)(1)`），把干净名字让给之后新建的那张。
> `active` 的那张永远用原名，折叠区里躺着的是带号的归档副本。

## 4. 索引设计原则

1. **所有跨用户查询必须走 `user_id` 前缀索引**，保证数据隔离和查询效率同时成立。
2. 时间范围统计字段（`occurred_at`、`eaten_at`、`started_at`）一律与 `user_id` 组成联合索引，顺序 `(user_id, 时间字段)`。
3. 高频筛选组合单独建索引（如 `tasks(user_id, status, due_at)`），不做过度索引。
4. 软删除过滤 `deleted_at IS NULL`（仅 `chat_sessions` 还有）作为最右条件，不单独建索引（选择性低）。

## 6. 数据隔离强制规则

1. 所有个人业务表的读写入口都从 `get_current_user` 取 `user_id`，**不接受请求体/查询参数中的 `user_id`**。
2. ORM 查询统一走仓库层封装方法（如 `TaskRepo.list_for_user(user_id, filters)`），禁止在路由里裸写 `db.query(Task)`。
3. 越权访问单条资源时返回 **404**（而非 403），避免泄露资源是否存在；仅在角色权限不足（如普通用户访问管理接口）时返回 **403**。
4. AI 工具函数签名不包含 `user_id` 参数，由依赖注入闭包传入（见 AI 设计）。
5. 管理员后台访问私人知识库的能力**不提供**任何接口。
